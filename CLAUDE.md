Handoff document. Read this before touching anything. It describes what exists, what is

---

## 1. What this is

A 2D **coin catcher** game (workshop project) built in Unity, from the Unity **Universal 2D**
template. A paddle moves left/right along the bottom of the screen and catches falling coins.
The project is at the very beginning: one scene, one script, one paddle object. Everything else
(coins, spawning, scoring, game over) is unbuilt.

Intended gameplay loop:

1. Coins spawn above the screen at random X positions and fall.
2. The player moves the paddle with A/D or ←/→.
3. Catching a coin increases the score; a missed coin may cost a life or end the run.
4. Score is shown in the UI. The game ends/starts fresh after a miss budget is exceeded.

## 4. Current scene: `Assets/Scenes/Main.unity`

Three root objects, in this order:

| Object | Components | Details |
|---|---|---|
| `Main Camera` | Transform, Camera, AudioListener, URP `UniversalAdditionalCameraData` | orthographic, **orthographic size 5**, position `(0,0,-10)`, background `(0, 0.49, 1)` |
| `Global Light 2D` | Transform, `Light2D` | global light type 4, white, intensity 1 |
| `Square` | Transform, SpriteRenderer, `Catcher` script | position `(0, -4, 0)`, scale `(2, 0.8, 1)`, tint `(1, 0.74, 0.005)`, built-in square sprite |

`Square` **is the player paddle**. It has no `Collider2D` and no `Rigidbody2D`, and the
`Catcher` component's serialized fields (`speed`, `limit`) are **not present in the YAML**, so
the inspector shows the script defaults (10 and 8) — because the script has no explicit field
serialization until Unity re-serializes it.

Camera math that matters: orthographic size 5 → visible half-height 5, half-width
`5 * aspect`. At 16:9 that is ≈ ±8.89, so `limit = 8` keeps a 1-unit-half-width paddle inside
the view at 16:9 but **clips it off-screen at narrower aspect ratios** (e.g. 4:3 → ±6.67).
If you keep a fixed `limit`, either derive it from the camera or clamp to
`camera.orthographicSize * camera.aspect - paddleHalfWidth`.

Scene YAML conventions (if you edit `.unity` by hand rather than through the editor):
file IDs are unique positive ints per file (except the `SceneRoots` sentinel `&9223372036854775807`);
script references are `m_Script: {fileID: 11500000, guid: <script guid>, type: 3}`; scene
objects must be listed in `SceneRoots → m_Roots` by their **Transform** fileID. Prefer editing
in the Unity editor; hand-edited YAML is easy to corrupt.

## 5. `Assets/Scripts/Catcher.cs` — current state (broken)

```csharp
using System.Numerics;      // ← wrong
using UnityEngine;

public class NewMonoBehaviourScript : MonoBehaviour   // ← wrong class name
{ public float speed = 10f; public float limit = 8f; ... }
```

Asset meta: guid `2052ac9bdb5f746828f18b078637534f`; the scene references
`m_EditorClassIdentifier: Assembly-CSharp::NewMonoBehaviourScript`.

Defects, in priority order:

1. **Class name ≠ file name.** A `MonoBehaviour` must be named exactly like its file
   (`Catcher`) or Unity cannot bind it and the scene component becomes a missing script.
   Rename the class to `Catcher`; the GUID in the `.meta` stays the same, so the existing
   scene reference keeps working.
2. **`using System.Numerics;`** pulls in `System.Numerics.Vector3/Vector2/Vector`, which
   collide with `UnityEngine.Vector3` etc. (CS0104 ambiguity where both are in scope) and the
   local `Vector pos = transform.position;` is a `System.Numerics.Vector` cast that cannot
   succeed. Remove the directive. Also `MathF` is unnecessary — use `Mathf`/`UnityEngine.Mathf`.
3. **Legacy input under the new Input System.** With `activeInputHandler: 1`,
   `Input.GetAxisRaw("Horizontal")` throws `InvalidOperationException` at runtime
   ("You are trying to read Input using the UnityEngine.Input class, but you have switched
   active Input handling to Input System package"). Pick one:
   - **(recommended)** Migrate to the Input System, using the existing `Player/Move` Vector2
     action (`Assets/Settings/InputSystem_Actions.inputactions`) via
     `InputSystem_Actions.PlayerActions` generated wrapper, or a plain
     `InputActionReference` / `Keyboard.current` read. Do not add a new action for this.
   - or set `ProjectSettings.asset → activeInputHandler: 2` (Both) and keep legacy calls.
     Cheaper, but goes against the template's intent — prefer the migration.
4. **Frame-rate dependence.** `transform.Translate(speed * input * Vector3.right)` ignores
   `Time.deltaTime`; the paddle moves twice as fast at 120 fps. Multiply by
   `Time.deltaTime` and use a design speed in units/second.
5. `Start()` is empty; delete it.

Reference implementation (Input System, no legacy axis, frame-rate independent — adapt rather
than paste blindly):

```csharp
using UnityEngine;
using UnityEngine.InputSystem;

public class Catcher : MonoBehaviour
{
    [SerializeField] float speed = 10f;
    [SerializeField] float limit = 8f;

    void Update()
    {
        var kb = Keyboard.current;
        if (kb == null) return;

        float input = 0f;
        if (kb.aKey.isPressed || kb.leftArrowKey.isPressed) input -= 1f;
        if (kb.dKey.isPressed || kb.rightArrowKey.isPressed) input += 1f;

        Vector3 pos = transform.position;
        pos.x = Mathf.Clamp(pos.x + input * speed * Time.deltaTime, -limit, limit);
        transform.position = pos;
    }
}
```

## 6. What remains to make the project complete

Nothing below exists yet. Build in this order; each step should leave the project playable.

1. **Paddle collider** — add a `BoxCollider2D` to `Square` (use the sprite bounds), layer
   tagging optional. Without a collider nothing can be "caught".
2. **Coin** — `Assets/Prefabs/Coin.prefab`: sprite + `CircleCollider2D` (trigger) +
   `Rigidbody2D` (kinematic or gravity-free, moved in script) + `Coin.cs` that falls at a
   configurable speed, destroys itself below the camera, and reports a miss.
3. **Spawner** — `CoinSpawner.cs` on an empty `GameManager`-style object: spawns coins above
   the view at random X within the camera's horizontal bounds on a timer (cooldown field).
   Independent of framerate.
4. **Catch detection** — a miss is best detected by the coin's Y passing below the paddle, not
   by trigger bookkeeping alone; a hit destroys the coin and fires a score event.
5. **Score + lives UI** — uGUI `Canvas` (Screen Space – Overlay) with score text, using
   `com.unity.ugui`. Keep UI code separate from gameplay code (events, not `Find`).
6. **Game over / restart** — simple state machine on the manager; a key or button restarts
   (reload the scene).
7. **Polish, only if the above works** — coin tints/sizes, catch sound (`AudioSource`),
   particles on catch, difficulty ramp (spawn interval / fall speed over time).

Conventions to follow:

- One `MonoBehaviour` per file, class name == file name, file in `Assets/Scripts/`.
- `[SerializeField] private` for inspector-tunable values; no public mutable statics.
- Cache `Camera.main` once in `Awake`, not per frame.
- No `GameObject.Find`/`SendMessage` in `Update`; wire references in the inspector or events.
- Every new asset gets its `.meta` committed (do not hand-write GUIDs; let Unity generate them).
- Delete/rename assets *inside* the editor so GUIDs and `.meta` files stay consistent.
- `.gitignore` already excludes `Library/`, `Temp/`, `obj/`, `Build/`, `*.csproj`, `*.slnx`.

Definition of done for a "complete" project:

- Play mode: paddle follows input at a constant units/sec on any refresh rate, stays fully on
  screen at 16:9 and 4:3.
- Coins spawn off-screen at random X, fall at a constant rate regardless of fps, are caught on
  contact, and are destroyed when caught or when they leave the screen.
- Score increments on catch, decrements/ends the run on a configurable number of misses, and
  restart works without a reload hang.
- Zero console errors or warnings; no missing scripts in `Main.unity`.
- `Main.unity` is the only enabled scene in `EditorBuildSettings`, and a StandaloneOSX build
  launches and plays.
